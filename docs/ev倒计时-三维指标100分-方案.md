## 〇、v2 核心修正（用户 2026-11-03 10:19 裁定）

> 「长截屏判断目标应该是这个页面内容已经全部截完整就算。指标算错了，我们算的应该不是长度，而是页面实际长度，只要截完了就算完成。它本来就两行，我们就截两行；本来就五个屏幕，我们就截五个屏。不能反过来为了指标去改内容，那叫本末倒置。」

据此废弃 v1 的「改产品补内容」路线（附录留档，不采用）。

**结论：`checkFramed` 的 `full` 维度用的是长度代理（`h > ch`），不是完整性判据。代理在单屏页上失效，且失效方向是惩罚正确行为。改为「滚到底证据 + 最低一屏高度」。**

## 三、判据改造规格（P0，工具侧）

### 3.1 病灶

`emubuddy_core.py` L3098–3108 已经测出「到底」：

```python
if md != prev_md5: break
print(f"  第{i}次 drag 无位移，重试 {retry + 1}/3")
else:
    print(f"第{i}屏滚动重试仍无位移 → 判定到底")
    break
```

`_fullshot_concat` 后输出 `全页长截图: <path> (192x490, 1/1 帧)`。

`parseShotOutput()`（server.js L982–1009）解析出 `dims` / `framesUsed` / `framesTotal`，
但 `checkFramed()`（L1103–1124）只用 `pngSize()` 的 `w/h` 判 `h > ch`。

**后果：采集侧测出的完整性结论被丢弃，评分只能靠长度猜。** 单屏页老实截一屏 → 判 `不是真长图` → 0 分。

### 3.2 新判据

```
checkFramed(route, type='full', evidence)
  ① 套壳正确性：w === cw(281)                    否 → no-frame
  ② 完整性：evidence.reachedEnd === true
           或无证据时退回 ③+旧长度判据           否 → incomplete
  ③ 最低高度：h >= ch(820)                        否 → 高度不足（疑似裁切/未套壳）
```

- 单屏页：滚 3 次无位移 → `reachedEnd=true` → 达标。两行截两行。
- 多屏页：必须真滚到底。少截一屏 → `reachedEnd=false` → 不达标。**严格性不降。**
- 滚到 `max_scroll` 上限仍未到底 → `reachedEnd=false`，reason `滚动上限耗尽，疑似未截全`（这条告警比现在准确，现在是靠高度猜）。
- 无 sidecar 的 `-long.png`（手工图/历史图）→ 退回 `h > ch`，reason 注明 `缺到底证据，按旧口径判定`。**历史 class 项目长图不受影响。**

### 3.3 防冒充（关键）

单屏页的长图与「只截了首屏的多屏页」**像素完全一致**（都是 192×490），看图无法区分。
因此完整性必须来自证据链，不能来自图像：

```
<截图根>/apps/countdown/cd-list-long.png    图（裸长图）
<截图根>/apps/countdown/cd-list-long.json   {"w":192,"contentH":490,"frames":1,"framesCollected":1,"reachedEnd":true,"endReason":"no-movement","maxScroll":6,"screenH":490,"ts":...}
```

约束：

1. sidecar 由采集进程（`_do_fullshot`）在滚动循环结束后**直接写**，不接受事后手填。
2. 评分侧只读 sidecar，`reachedEnd` 必须为布尔 `true`。
3. sidecar 缺失 = 无证据，退回旧口径。**这比现状更严**：现在一张够高的任意图就能过，以后还得有滚动记录。
4. **`reachedEnd` 有多假信号，必须看 `endReason`**（2026-11-03 实跑发现）：
   - `no-movement`：重试耗尽无位移 → 真到底
   - `frame-jump`：拼接未吃满采集帧（零重叠）→ 画面中途切换，**结论作废**
   - `max-scroll-exhausted`：跑满上限仍未到底 → 可能没截全
   - `frame-missing`：帧缺失中断
   
   实测：deploy 后立即截图，滚到第 4 屏无位移被判「到底」，而 4 帧只拼了 1 帧、画面还是上一个应用残留。采集侧已在落盘前把这种情形降级为 `frame-jump` + `reachedEnd:false`，评分侧不必再判，但日志排查时要认这个字段。

## 六、风险

1. **sidecar 与图脱节**：先出图后写 json，中途失败会留下无证据的图。缓解：`_do_fullshot` 内先写 json 再 `os.replace` 覆盖正式图，原子顺序保证不出现孤儿图。
2. **md5 误判到底**：页面有动画/闪烁时连续两次截图 md5 恒不同，会一直滚到 `max_scroll`。现状已有此风险，不是新引入；缓解：`max_scroll` 耗尽时 `reachedEnd=false` 明确告警，不再静默产出一张超长废图。
3. **旧长图回归**：class 项目 118 张历史图无 sidecar。缓解：缺证据退回 `h > ch`，行为与改造前完全一致。
4. **两个仓改动不同步**：server.js 先上、采集侧未上，则所有长图缺证据 → 全部退回旧口径（不报错，只降级）。缓解：先上采集侧（多写一个 json 不影响旧逻辑），再上评分侧。
5. **空壳文档凑分**：技术上可行，明确不采用。

## 附录：v1 方案（已废弃，留档说明为何不用）

v1 提出「A 改产品补内容 / B 放宽口径 / C 白名单豁免」三选一，推荐 A。该框架错误在于**接受了「长图必须超一屏」这个伪前提**，把指标缺陷转成了产品改版需求。
