# 手环快应用「应用内语言切换」核心技术实现流程

> 适用：Vela / 快应用（手环）任意工程，要在**应用内**切换界面语言（不依赖系统语言）。
> 已验证：`ev/countdown` 设置页（2026-11-15，Xiaomi Smart Band 9 真机通过）。
> 前置结论与坑：`pit-20261115-189`、`pit-20261115-191`；本文是「怎么做」的完整流程。
> 北京时间 2026-11-15 +0800。

---

## 一、先讲清楚为什么必须自建（否则会走一整圈弯路）

Vela 的 i18n 有两条能力，很多人（包括我们）第一轮把它们混为一谈：

| 能力 | 是否可用 | 结论 |
| --- | --- | --- |
| 资源包多语言：`src/i18n/*.json` + `$t()` | ✅ 可用 | 界面语言**跟系统走**，系统切了它就变 |
| 应用内主动切语言：`configuration.setLocale()` | ❌ 无效（1050 / 1060 均实测静默 no-op） | 不抛错、`getLocale()` 不变、界面不变 |

所以「点了能切」这件事**只能自己做**：词表放 JS、语言状态放 `data`、模板取字面量属性渲染。

**判定 API 是否真的生效的唯一口径**：调用前后各取一次 `getLocale()` 对比。
`before === after` ⇒ API 层无效（别怀疑自己的代码）；`after` 变了但界面没变 ⇒ 资源或匹配层问题。二者修法完全不同。

---

## 二、五个步骤（照做即可，单页约 60 行）

### 步骤 1：词表落地为 JS 模块

新建 `src/common/i18n.js`：

```js
const DICT = {
  zh: { settings: { title: '设置', language: '语言', /* … */ }, theme: { classic: '经典黑' /* … */ } },
  en: { settings: { title: 'Setup', language: 'Lang', /* … */ }, theme: { classic: 'Dark' /* … */ } },
  ja: { settings: { title: '設定', language: '言語', /* … */ }, theme: { classic: 'ダーク' /* … */ } }
}

// 只按字面量取属性；模板侧绝不拼 key
function getT(lang) { return DICT[lang] || DICT.zh }

// 偏好 > 系统语言；读不到系统语言时落中文（defaults 恒中文）
function langFromPref(pref, sysLang) {
  if (DICT[pref]) return pref
  const s = String(sysLang || '').toLowerCase()
  if (!s) return 'zh'
  return s.indexOf('zh') === 0 ? 'zh' : (s.indexOf('ja') === 0 ? 'ja' : 'en')
}

module.exports = { DICT, getT, langFromPref }
```

**要点**

- 词条**不要手抄**：用 Node 从现有 `src/i18n/*.json` 生成，保证与框架词表同源，避免两份真相。
- 语言标识用**完整 locale 字符串**（`auto` / `zh-CN` / `en` / `ja-JP`），不要用布尔 `isEnglish`——加第三门语言时不用改调用方。
- 键名**不要带语言标识**，`defaults` 恒中文（与框架侧同一套约定）。
- 新增语言 = DICT 里加一个顶层键 + 数组里加一项，模板零改动。

### 步骤 2：页面挂 `t` 到 data

```js
const I18N = require('../../common/i18n.js')

data: {
  t: I18N.getT('zh'),      // 模板默认中文，onInit 再按偏好覆盖
  themeName: ''            // 需要"翻译后的动态值"时，脚本先查好再下发
}
```

### 步骤 3：模板改成取属性

```html
<!-- 之前 -->
<text>{{ $t('message.settings.title') }}</text>
<text if="{{ themeKey === 'classic' }}">{{ $t('message.theme.classic') }}</text>
<!-- 之后 -->
<text>{{ t.settings.title }}</text>
<text>{{ themeName }}</text>
```

**两个禁止**

1. **禁止在模板里拼 key**：`$t('message.theme.' + key)` 构建能过，**运行即崩**（进程直接消失）。同理 `t.theme[key]` 也不要写进模板。
2. **禁止在脚本里用 `this.$t`**：返回的是原始 key，不是词条。

需要动态值时的正确做法：脚本里查好（`self.themeName = self.t.theme[k]`），模板只渲染结果字符串。

### 步骤 4：切换入口

```js
cycleLocale() {
  const next = LOCALES[(LOCALES.indexOf(this.locale) + 1) % LOCALES.length]
  this.locale = next
  this.localeLabel = this.labelOf(next)   // 值列文案，短标识
  this.applyLang(next)                    // 先换字典（立即生效）
  storage.set({ key: LOCALE_KEY, value: next })  // 再落盘
}

applyLang(pref) {
  let sysLang = 'zh'
  try {
    const configuration = require('@system.configuration')
    const loc = configuration.getLocale()
    if (loc && loc.language) sysLang = String(loc.language)
  } catch (e) {}
  const lang = I18N.langFromPref(pref, sysLang)
  this.t = I18N.getT(lang)
  const names = this.t.theme
  this.themeName = (names && names[this.themeKey]) || this.themeName
}
```

**关键：不需要 `router.replace` 重建页面。** 只改 `data.t`，模板自动重算。上一版那套「切完延迟 150ms 重建页面」是给框架 `setLocale` 擦屁股的，现在是纯负收益（会闪屏）。

### 步骤 5：冷启动恢复

`app.ux onCreate` 读 storage，把首次语言设进全局；页面 `onInit` 各自 `applyLang`。

```js
storage.get({ key: 'cd_locale', success: function (v) {
  if (LOCALES.indexOf(v) >= 0) applyLang(v)   // 不存在的值一律当 auto
}})
```

框架侧 `setLocale` 可以保留（1060+ 若将来真支持，属于白捡），但**不要依赖它**。

## 三、多语言版式的硬约束（ev-six，总纲 §3.21 第 9 条）

自建 `t()` 解决"能不能切"，不解决"放不放得下"。四个卡点：

1. **英文单词 ≤8 字母 @28px**（卡片/标题 ≤7，状态大字 ≤5，24px ≤9）。超了就换一词化译法，**禁止缩字号、禁止截断、禁止省略号**。
2. **字号四档 `44/30/28/24` 跨语言完全不变**。
3. **行级判据**：同一 UI 行的译文总 P ≤ 原文总 P（双列两列之间可互相借额度，单条略宽不算失败）。
4. **宽度系数**：汉字 1.0P、拉丁字母 0.55P、空格 0.3P、**日语全角（含片假名）1.0P**。

日语特殊提醒：片假名外来语极易超宽（`バイオレット` = 6.0P，正好顶满 168px@28px 的容量）。能压就压：`バイオレット → ムラサキ`、`クラシック → ダーク`。

## 四、自测清单（改完先跑这四条，别上机）

1. **key 对齐**：zh / en / ja 三份词表 key 集合逐条 `deepStrictEqual`，缺一条即失败。
2. **兜底**：`getT('unknown')` / `getT(undefined)` 必须返回 zh，页面永不渲染 `undefined`。
3. **偏好解析**：显式偏好压倒系统语言；`auto` 才看系统；系统语言缺失落中文。
4. **词长**：扫所有译文，断言每个英文单词 ≤8 字母。

这四条已固化为 `ev/countdown/test/i18n.test.js`（7 项），示例可直接搬。

## 五、迁移其它页面的最小动作表

| 页面 | 改动 |
| --- | --- |
| 昵称页 / 主题页 / 诊断页 | `data` 加 `t` + `onInit` 调 `applyLang`；模板 `$t(...)` → `t.xxx` |
| 首页（动态文案多） | 同上，但**天数单位、分组标题**这类要先按新语言重算，别只换静态文案 |
| 任意页 | 若含动态拼接（如"剩余 3 天"），把拼接逻辑搬进脚本函数，模板只渲染结果字符串 |

**进度（2026-11-15 20:30）**：设置页 / 昵称页 / 主题页 / 诊断页 **已完成**；剩 cd-list（首页）、cd-edit、cd-name 三页。其中 cd-list 与 cd-edit 中文量最大（动态拼接多），要单独排期。

**两类页面的差别，务必分清**

- **静态文案页**（昵称、主题、诊断）：模板直接把 `$t(...)` 换成 `t.xxx` 即可，`t` 一换全页跟着变。
- **数据驱动页**（主题页的 11 个主题名、首页的天数单位）：文案来自 `data.js` 返回的对象，**光换 `t` 不会变**，必须在拿到数据后按字典重建数组（见主题页 `applyLang()`：浅拷贝每项再覆盖 `name`，不要改 `data.js` 里的模块数据，否则会污染整个应用）。

**加词条的固定动作**（本轮新增脚本，别再手抄字典）

```bash
# 1. 改 src/i18n/{zh-CN,en,ja-JP,defaults}.json 里的 message.<页>.*
# 2. 重新生成 DICT 字面量（不许手改 src/common/i18n.js 的字典段）
node scripts/gen-i18n.js
# 3. 校验 key 三语对齐 + 文案宽度
node test/i18n.test.js && node scripts/check-i18n-copy.js
```

`gen-i18n.js` 只替换 `const DICT = {...}` 这一段，文件里的注释与函数原样保留；若哪天 i18n.js 结构调整，脚本会直接报错而不是静默写坏。

**校验行要按页面真实布局给宽裕**：设置页是双列 `space-between`，只能 0 宽裕；诊断页标签 24px 独占一行、可用整行 168px，可给 1.5P；定宽按钮 176px 给 2.0P。**别把某个页面的宽裕值套到另一个页面**，那等于自欺。

**全量迁移的两个收尾动作**

1. 删掉 `src/i18n/*.json` 与 `$t` 调用（两套机制并存会让后来人分不清谁是真相）。
2. `minPlatformVersion` 退回 1050 —— 自建方案不依赖 `configuration`，没必要为它缩窄兼容面。

## 六、这个方案解决不了什么（提前说清）

- **系统级语言**：改不了，也不该改。应用内切换只影响本应用。
- **系统自带的输入法 / 系统组件**：它们跟系统语言，不跟我们（但我们**自建**的 `input-method` 组件是可控的，见第七节）。
- **应用名** `manifest.name`：不在资源体系内，属单独议题。
- **首屏语言闪变**：`app.ux` 读 storage 是异步的，理论上首帧可能是中文再切过去。当前设置页在 `onInit` 就切换，肉眼未见闪；若将来首页也有此问题，解法是在 `app.ux` 里同步预置一个默认值，别等回调。

## 七、输入法语言跟随界面语言（2026-11-15 加，关键复用点）

**前提结论**：本项目昵称页用的不是系统输入法，而是工程内自建的 `src/components/InputMethod/InputMethod.ux`（rect 全键盘）。所以「输入法能不能切日语」**完全由我们决定**，与平台能力无关 —— 这是自建键盘带来的额外红利。

**组件既有的三态**（读源码即可确认，无需改造词库）：

| 界面语言 | 键盘 `lang` | 词库 | 行为 |
| --- | --- | --- | --- |
| 中文 | `cn` | `dictionary/cn.txt` | QWERTY 打拼音，出汉字候选 |
| 英文 | `en` | 无（纯字母） | 只出字母，大写可切 |
| 日语 | `jp` | `dictionary/jp.txt` | QWERTY 打罗马字，出假名候选 |

左上角 `lang` 键原本就按 `cn → en → jp → cn` 循环，`jp` 的 UI 分支、`jp.png` 图标、`numFlag_jp` 数字层全部齐备。**缺的只有一点**：`data.lang` 写死 `"cn"`，所以日语界面下仍先弹中文拼音，用户得手动按一下。

**三步接线（共约 25 行）**

1. `src/common/i18n.js` 增 `imeLangOf(pref)`，把界面语言映射成键盘语言。注意**不是恒等映射**：`zh→cn`、`ja→jp`、`en→en`，未知一律 `cn`。同时抽出 `resolveLang(pref)`（取系统语言 + 偏好优先），供 `forPref` 与 `imeLangOf` 共用，避免两处各算一遍导致错位。
2. `InputMethod.ux` 加 `initlang` prop（默认 `"cn"`，保持对其它调用方零影响），`onInit` 里若为 `en/jp` 就赋给 `this.lang`；再加一个 `watchInitLangPropsChange` 兜住「页面异步读 storage 比键盘挂载晚到」的时序。
3. 宿主页把同一个 `pref` 同时喂给词表和键盘：

```js
storage.get({
  key: 'cd_locale',
  success: function (v) {
    self.t = I18N.forPref(v || 'auto')        // 界面文案
    self.imeLang = I18N.imeLangOf(v || 'auto') // 键盘初始语言
  }
})
```

模板：`<input-method initlang="{{ imeLang }}" ... />`

**为什么同一个 pref 出两个值**：界面文案是三份 JSON 的字典键（`zh/en/ja`），键盘是组件内部三态（`cn/en/jp`），两套命名不同。必须由 `imeLangOf` 一处做映射，页面里绝不能自己写 `pref === 'ja-JP' ? 'jp' : ...`，否则将来加语言时又要满地找。

**边界（别过度承诺）**

- 只改**初始**语言。用户进页后按 `lang` 键仍可自由切走，我们不去纠正——这是用户当前会话的明确意图，优先级高于偏好。
- 系统语言变化不会实时影响已挂载的键盘（`initlang` 只在 prop 变化时同步）。
- 键盘语言与界面语言是**两条独立状态**：界面已切日语但用户手动把键盘切回 `cn`，属允许状态，不要试图锁死。
- 这条链路只覆盖昵称页等**用自建键盘**的页面；将来若改用系统输入法，本节全部作废。
