## 二、核心认知纠正：`screentype` 不是"屏幕形状声明"

这是本次最重要的一条。`screentype` 参数**不是告诉组件"我的屏幕是什么形状"**，而是**选择哪一套键盘实现**。组件里三套实现彼此完全独立，各自写死了自己的尺寸和排布方式：

| 分支 | 容器宽度 | 容器高度 | 依赖 `screenWidth` | 键位排布 |
|---|---|---|---|---|
| `rect` | `100%`（自适应） | **255px** | ❌ 完全不依赖 | flex 行 + `scroll-x` 横向滚动 |
| `pill-shaped` | `100%` | **305px** | ✅ `(screenWidth-192)/2` 算留白 | `position:absolute` 固定 top/left |
| `circle` | **480px 写死** | 321px | ❌（写死） | `position:absolute` 固定坐标 |

三档的关键差异不在"圆形/方形外观"，而在**是否依赖运行时拿到的屏幕宽度**和**容器高度**。

**所以"胶囊屏却要用矩形键盘"并不矛盾**——rect 只是"方键 + 横向滚动"这套实现的代号，任何形状的屏都能跑，只要空间够。

## 三、为什么 rect 能开、另外两档打不开

按可能性排序：

### ① 只有 rect 不依赖异步获取的 `screenWidth`（最可能）

组件源码：

```
screenWidth: 336,     // 初值，注释：'针对 screenShape 为 rect 的设备，会自动获取'
adjustScreenWidth(){ device.getInfo({ success: d => this.screenWidth = d.screenWidth }) }
```

调用点是 `if (this.screentype === 'rect' || this.screentype === 'pill-shaped')`，但 **`screenWidth` 是异步写入的**。在回调返回之前：

- `pill-shaped` 按初值 336 算留白：每边 `(336-192)/2 = 72px`
- 内容总宽变成 **336px，塞进 212px 的屏，溢出 124px**
- 而 212 屏上真实值算出来应该是每边 10px

`rect` 分支一个像素都不算，所以完全不受这个时序问题影响。

### ② 容器高度 305 vs 255

520 的屏高上，pill 要占 305，加上页头、输入框、候选区必然顶爆；rect 的 255 还能留出余量。

### ③ 绝对定位对容器高度极敏感

pill / circle 大量使用 `position:absolute` + 固定 `top/left`，父容器一旦比设计值矮（或高），子元素直接跑出可视区，Vela 上表现为白屏或整页不渲染。

### ④ `circle` 分支写死 480×321

在 212 宽的屏上溢出 2.26 倍，属确定性失败，不需要再测。

## 四、课程表的实现核对：它确实是"自动判断"，这就是问题所在

`ev/class-schedule/src/pages/chinese-input/chinese-input.ux`：

```js
screenType: "pill-shaped",          // 默认值（第 70 行）
onInit() {
  device.getInfo({ success: function(data) {
    var shape = data.screenShape || "circle"     // 取不到就当圆形
    if (shape === "capsule") { shape = "pill-shaped" }   // 胶囊 → 映射成 pill-shaped
    self.screenType = shape
  }})
}
```

模板：`screentype="{{ screenType }}"`

**这条链条是：系统上报 `screenShape` → 映射（capsule→pill-shaped）→ 传给组件。**

### 你的基本逻辑成立

> "输入法就一套，屏幕根据系统对型号的判断自动匹配；小米 11 匹配到了胶囊屏，但胶囊那套打不开，所以出了问题。"

**成立，且这就是全链路解释。** 手环 11 上报 `capsule` → 课程表映射成 `pill-shaped` → 走 305px 高、依赖 `screenWidth`、绝对定位的那套实现 → 打不开。

### 但有一个分支尚未确定

**手环 10 上报的 `screenShape` 是什么，我们还不知道。**

- 如果手环 10 上报 `rect` → 它自动走 rect → 能用。那么结论是"**胶囊这套在 Vela 上整体不可用**"，与机型无关。
- 如果手环 10 也上报 `capsule` → 它也走 pill 却能跑 → 说明 pill 分支是"**在 11 上特有地崩**"（可能是 `device.getInfo` 返回时序、屏高、或固件渲染差异）。

这个分支决定修法方向：

- 前者 → 直接把全局默认改成 rect 即可，一劳永逸
- 后者 → 需要针对 11 做机型特判，或修 pill 分支

**目前证据偏向"胶囊屏这套整体不可用"**：第 1、4、5、7 四项凡是走 pill 的全灭，无一例外。

## 五、连带结论：课程表手环 11 的输入法不可用，根因同源

如果第四节前一条成立，那课程表在**所有上报 `capsule` 的机型**上中文输入都不可用——这正好对应你说的"手环 11 上目前用户都不能用"。

也就是说，这不是倒数日新应用的问题，是**课程表（以及所有照抄它做法的页面）共有的缺陷**：信任了系统上报的屏型，而没有对映射结果做可用性兜底。

修法（两个项目都要改）：

```js
// 错误做法：完全信任系统上报
screenType = data.screenShape === "capsule" ? "pill-shaped" : data.screenShape

// 应改为：只在确认可用的分支上做映射，其余一律回落 rect
var shape = data.screenShape
screenType = (shape === "rect") ? "rect" : "rect"   // 即：强制 rect
```

**代价**：胶囊屏上按键是方的，视觉不贴合机身弧线。
**收益**：键盘能用。以当前证据看，这个交换是划算的——不可用的漂亮布局没有价值。

## 六、附带纠正的两条旧判断

### ① "右侧被裁"是误读

之前我在模拟器里判定"QWERTY 到 E 就断，属布局溢出 bug"。实际那是 `scroll-x` 横向滚动的设计——每个键 60px，212 宽的屏本来只显示约 3.5 个，其余靠滑动手势。手环 9（192 宽）时代的弧形轮盘键盘就是这个思路。

**教训：不能凭截图判定溢出，必须先确认容器是否可滚动。**

### ② "模拟器与真机行为不同"被真机否掉

我曾推测"真机会把 480 画布映射到屏宽，模拟器不做，所以真机可能正常"。真机结果：pill 在真机上也起不来。**模拟器这次没有骗人，是我判断偏了。**

## 七、本次暴露的一个自身缺陷（下版必修）

诊断页目前记录：版本、机型、屏幕宽高、系统版本、词库读取返回码、脚印记录。

如果当初记了这一项，这次就能直接确定第四节那个未定分支，不必再问用户一轮。测试机会珍贵，**每一条能从设备自动采集的信息都不该依赖用户描述**。

| 字段 | 用途 |
|---|---|
| `screenShape`（原始值） | 确认系统上报 capsule / rect |

| 实际渲染的 `screentype` | 确认映射后的结果 |
