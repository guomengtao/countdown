# 「语言」行点了不生效 —— 根因分析（2026-11-15）

> 现象上报：Tom 真机实测，Xiaomi Smart Band 9，`Ev倒数日 0.6.23-vc163`
> 关联坑：`pit-20261115-189`、`pit-20261115-190`
> 关联文档：`docs/多语言设置页试点与日语扩展-20261114.md`
> 北京时间 2026-11-15 +0800

## 〇、一句话结论

**不是应用代码写错了，也不是"系统不支持多语言"，而是 1050 平台不支持"应用自己改语言"。**

拆开说三句：

1. `configuration.setLocale()` 在 `minPlatformVersion: 1050` 上是**空操作（no-op）** —— 不报错、不抛异常、返回正常，但什么也不做。这属于最恶劣的"静默成功"形态。
2. 你看到的 **EN 是我们自己的一个文本变量**，不是翻译结果，所以它能变；其余汉字由框架查 `zh-CN.json`，框架的 locale 没变，所以一个都没变。
3. "闪一下"是我们自己 `router.replace` 重建页面造成的，它证明"页面重建了"，**不证明"语言切了"**。

所以：**能力缺失 + 产品假设错误**，不是 bug；但"点了没有任何提示"这一层，是我们的体验缺陷（见 §五）。

## 一、你的三个观察，逐条对上

| 你看到的 | 真实发生的 | 代码位置 |
| --- | --- | --- |
| 点击后页面**闪了一下** | 我们自己 `storage.set` 成功后延迟 150ms 执行 `router.replace({uri:'/pages/settings'})`，整页销毁重建 → 视觉上闪一下 | `src/pages/settings/settings.ux:215-226` |
| 值变成了 **EN** | 这是 `data.localeLabel`，由 `labelOf(v)` 直接返回字面量 `'EN'`，从 storage 读回即渲染。**它与 i18n 框架完全无关**，纯自家状态 | `settings.ux:186-191` / `193-207` |
| 其他汉字**全在** | 所有汉字都是 `$t('message.xxx')`，由框架按"当前 locale"去 `src/i18n/*.json` 查表。当前 locale 仍是 `zh-CN` → 命中 `zh-CN.json` → 全是中文 | `settings.ux` 模板 + `src/i18n/` |
| 退出再进**还是中文** | 冷启动 `app.ux onCreate` 确实按存下的 `'en'` 又调了一次 `setLocale` —— 但**还是空操作**；框架按系统语言 `zh-CN` 匹配到 `zh-CN.json` | `src/app.ux:31-36` |

关键点：**"EN 能变"和"汉字不能变"不矛盾**。前者是纯 JS 字符串，后者要过框架的 locale 匹配。你的测试其实非常到位 —— 正好把这两层劈开了。

## 二、根因三层，越往下越硬

### L1 应用层：已排除（这层没问题）

- 状态改了 ✅（`this.locale = next`）
- 持久化写了 ✅（`storage.set({key:'cd_locale', value:'en'})`）
- 冷启动恢复了 ✅（`app.ux onCreate` 读 storage 再 apply）
- 页面重建了 ✅（`router.replace`）

这四步全都正确执行了 —— 否则你不会看到 EN、也不会看到闪。链路是通的，断点在下一层。

### L2 API 层：`setLocale` 在 1050 上不生效

- 快应用联盟 API 文档里 `configuration.setLocale` 标注的可用版本是 **1060+**。本工程 `minPlatformVersion: 1050`。
- 实测行为：**调用不抛错、`getLocale()` 前后返回值完全不变**。既没有 `fail` 回调，也没有异常 —— 所以 `try/catch` 抓不到任何东西，代码"看起来"成功了。
- **对照实验（决定性）**：把系统语言用 `adb shell setprop persist.locale en_US` 改掉后重启应用，界面立刻全英文。这一条同时证明了三件事：
  - `src/i18n/en.json` 打包进去了 ✅
  - 框架的 locale 匹配链（`zh-CN` → `zh` → `zh-*` → `defaults`）工作正常 ✅
  - 唯一卡住的就是「应用向系统请求切 locale」这一步 ❌

也就是说：**资源和翻译都没问题，是"改语言"这个动作在 1050 上不存在。**

### L3 框架层：Vela 的 locale 本来就是「启动时注入」的

官方文档明确：**"应用重新进入时语言环境会重置为系统语言"**。

这句话本身就是答案 —— 它说明 locale 在 Vela 的模型里是一个**会话级、启动时由系统注入**的量，不是"运行时可写的页面变量"。`setLocale` 即便在 1060+ 可用，也只是在**本次会话内**覆盖一下，重启即失效，所以才需要我们每次冷启动重设一遍。

**结论：「支持多语言」和「支持应用自己切语言」是两种不同能力。**
你的手环**支持前者**（资源匹配、`$t`、`defaults` 回退全都正常），**在 1050 上不支持后者**。

## 三、为什么声明了 `system.configuration` 还是不行？

这是上一轮已经踩过的坑，容易误判，写清楚：

| 声明 `features: system.configuration` | 作用范围 |
| --- | --- |
| ✅ 解决 | 构建链允许 `require('@system.configuration')` —— 不声明的话 `aiot release` 直接报 `missing feature` 中止 |
| ❌ 不解决 | 运行时**能力是否存在**。能力取决于 `minPlatformVersion` 与固件实现 |

**声明 = 允许编译，不等于允许生效。** 这是两码事，`manifest.json` 那个 feature 不要动——它现在是必需的。

## 四、为什么它"看起来像 bug"（这一层确实是我们的问题）

`src/pages/settings/settings.ux:241-243`：

```js
} catch (e) {
  // 平台 <1060 或未开放 configuration 时静默降级：仍跟随系统语言，不影响其他功能。
}
```

这段注释当时是"稳妥兜底"，实际效果是**把唯一的诊断线索吃掉了**。加上 `setLocale` 本身在 1050 上根本不抛错，于是形成双重静默：

```
用户点击 → 状态变了 → 存储写了 → 页面重建了 → 语言没变 → 没有任何提示
```

如果当时加了一行探针，问题在第一次装机 30 秒内就能定位：

```js
function applyLocale(v) {
  try {
    const configuration = require('@system.configuration')
    const before = configuration.getLocale()          // 关键：前后各取一次
    const parts = v.split('-')
    configuration.setLocale({ language: parts[0], countryOrRegion: parts[1] || '' })
    const after = configuration.getLocale()
    probe.mark('locale', 'apply', [v, before && before.language, after && after.language].join('/'))
    // before.language === after.language === 'zh-CN' ⇒ 确认 no-op
  } catch (e) {
    probe.mark('locale', 'apply-fail', String(e))
  }
}
```

**判定口径**：`before == after` 就是 no-op（API 层无效）；`after == en` 但界面仍是中文，则是资源/匹配层问题。这两种完全不同的故障，靠这一行就能分开。

## 五、判定结论

| 维度 | 判定 |
| --- | --- |
| 是不是代码 bug | **不是**。状态、存储、重建、冷启动恢复四步全部正确 |
| 是不是系统不支持 | **半是**。支持多语言（资源 + 匹配），**不支持应用内切 locale（1050）** |
| 有没有体验 bug | **有**。点击无任何反馈、无降级提示，用户无法区分"点了没生效"和"点了坏掉了" |
| 该不该保留这一行 | 见 §六 —— 要么让它真能用，要么别让它假装能用 |

## 六、三条出路（按性价比排）

### 方案 A：验 1060+ —— 成本最低，建议**第一个做**

只改 `src/manifest.json` 一个字段：`minPlatformVersion: 1050 → 1060`，重新打包装机试一次。

- **成本**：改一个数字 + 一次装机，半小时内出结论。
- **前提**：手环 9 固件确实 ≥ 1060（需实测确认，`system.device.getInfo()` 可读）。
- **若生效**：`setLocale` 直接可用，现有代码一行不用改，`router.replace` 那套重建逻辑也刚好配合得上。
- **若不生效**：说明 Vela 侧压根没实现这个能力，直接跳方案 B，且这个结论要进坑库（比现在还值钱）。
- **风险**：`minPlatformVersion` 抬到 1060 会缩小可装设备面。个人自用无所谓，上架要权衡。

### 方案 B：自建 `t()` 查表 —— 真能切，但要改渲染方式

把文案从 `src/i18n/*.json` 搬到 JS 字典，页面里用 `this.t('settings.title')` 取，语言用一个 `data.lang` 驱动。

- **优点**：完全不依赖框架 locale，**100% 可控，能切、能持久化、能即时刷新**（改 `data.lang` 模板自动重算，连 `router.replace` 都可以省）。
- **成本**：每页文案都要从 `$t` 改成 `this.t`。设置页 10 条很少，但 cd-list / cd-edit / cd-name / theme / nickname / diag 全量翻就上量了。
- **注意**：这条路反而**绕开了**上一轮踩的两个坑（脚本作用域 `$t` 返回原 key、模板动态拼 key 崩溃），因为自建 `t()` 本来就是纯 JS 查表 —— 主题名那种"11 个 key 得手写 11 条字面量分支"的丑陋写法可以彻底删掉。
- **代价**：`$t` 和自建 `t()` 两套机制并存会很脏，要做就得一次性全迁，别半套。

### 方案 C：摘掉/改造这一行 —— 诚实的降级

- 最省事：删掉「语言」行，回到 7 项列表（正好也是原来 378px 不溢出的状态），应用**只跟随系统语言**。
- 折中：保留这一行但改成**只读展示**，值为 `Auto`/跟随系统，点击跳说明页（或直接不响应）—— 至少不会让人以为能切。
- 若走 C，`app.ux` 里的 `applyLocale` 和 `cd_locale` 存储也一并清掉，别留死代码。

### 建议

**先花半小时验 A。** A 是唯一"可能一行代码都不用改就解决"的路径，而它失败也有价值 —— 能把手环侧的确定结论钉进坑库。

- A 通过 → 收工，补一条 `probe` 记录固件版本即可。
- A 不通过 → 二选一：想要可切换就上 B（并规划全量迁移），想省事就上 C（诚实的跟随系统）。
- **不论走哪条，都要先把 §四 那行探针加上**，否则下次还是两眼一抹黑。

## 八、要写进坑库的结论

1. `configuration.setLocale` 在 `minPlatformVersion 1050` 上是**静默 no-op**：不抛错、`getLocale()` 不变、界面不变。**不要用"有没有抛异常"来判断 API 是否可用**，必须在调用前后各取一次 `getLocale()` 对比。
2. 「多语言资源可用」≠「应用内可切换语言」。Vela 的 locale 是**启动时由系统注入**的（官方明写"重新进入时重置为系统语言"），`setLocale` 至多是会话级覆盖。
3. `manifest.features` 声明只解决构建期 `missing feature`，**不代表运行时具备该能力**；能力看 `minPlatformVersion` + 固件。
4. 凡是"调了 API 但界面没反应"的场景，`try/catch` 里第一件事是**记探针**，不是写"静默降级"注释。
